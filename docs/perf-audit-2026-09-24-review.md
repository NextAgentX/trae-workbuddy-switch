## ★ 撤回：P1-4 sticky 表「内存泄漏」不成立

**我原先的结论**：「粘性表 `gc` 从不被调度 ⇒ `bindings` 无界增长 ⇒ 潜在内存泄漏」。

**复核后的事实**：`StickyTable` 的公开方法有 `new` / `ttl_ms` / `len` / `is_empty` / `get` / `bind` / `unbind` / `gc`，而**全仓（排除 `sticky.rs` 自身）只有一处调用**：

```
crates/buddy-switch-gateway/src/routes/status.rs:29
    let sticky_sessions = state.sticky.read().await.len();
```

⇒ `get` / `bind` / `unbind` / `gc` **在生产代码里一个都没被调用**，`sticky_sessions` 永远是 `0`。

**正确结论**：**不存在内存泄漏**（表恒为空，无增长）。真实情况是——**整套粘性会话机制未接线**，属未完成/预留功能。这比「泄漏」性质完全不同：它不会随时间恶化，但按本项目「不保留死代码」的纪律，应当明确它的去留（接上写路径 / 或连 `sticky_ttl_ms` 配置项与 status 字段一并移除）。

**顺带发现一条纪律**（决定了「接上」该怎么做）：`crates/buddy-switch-server/src/main.rs:33-57` 定义了一个**后台任务注册表**，注释明确写着：

> 「后台任务的**存在性**必须是**数据**，而不是散落在 `spawn_background_loops` 里的 `tokio::spawn` 调用……**登记即执行**——不要在本表之外直接 `tokio::spawn` 后台循环。」

⇒ 若将来要加粘性表的后台 GC，**必须登记进 `BackgroundTask` 枚举**，否则违反该纪律且会被测试拦下。

**教训**：「函数存在但从无调用」不能直接推成「迟早会泄漏」。**必须先查写入路径是否真的被调用** —— 这正是本项目「『某文件存在』≠『某行为发生过』」那条纪律的同类错误，我这次踩了。

## P0-1 进程枚举：确认为真问题（遗漏），但**不是热路径**

**「是不是有意为之」→ 否，是遗漏。** 最强证据是**同一团队在另一个文件里已经做了这个优化，还写明了理由**：

```
crates/buddy-switch-core/src/modules/trae/platform.rs:1079-1083
/// 只调一次 `tasklist` 拿到全量列表再逐个名字比对，而不是「每个候选名各调一次
/// `tasklist /FI IMAGENAME eq ...`」—— 后者在装了多个渠道时要起 4 个子进程，
/// 这里只起 1 个。
```

该优化由 `19287bb fix(trae): 重写授权登录契约…` 引入（**晚于**初始提交）。而 `process.rs:519-540` 的逐映像名版本来自初始提交 `461827e chore: 初始化 Git 版本管理并纳入项目源码` —— 即**改 Trae 侧时没顺手改 WorkBuddy 侧**。

**但严重度必须下调，因为路径是冷的**（已查全部调用者）：

| 调用者 | 场景 | 频率 |
|---|---|---|
| `is_workbuddy_running_for`（`process.rs:1290/1311/1316/1337`） | 状态探测 | 服务端已有 **3s 缓存**（`server/api.rs:28-46`）；Tauri 侧 `get_status` **已 async + spawn_blocking**（`commands.rs:88-94`，注释写明就是为这个子进程） |
| `wait_windows_pids_gone`（`process.rs:1368/1380`、`codebuddy_cn_ide.rs:753/765`） | **切换 / 结束客户端** | 冷路径，但**每轮 500ms 轮询 × 每 PID 一次**，是会直接叠加到切换等待时间上的那一段 |

⇒ **修正后的定性**：真问题，收益确定（Global 区域 564ms → 141ms；等待轮询从 N 次/轮 → 1 次/轮），但**项目已经刻意缓解了最痛的症状**（主线程阻塞、状态探测频次）。**最有价值的是 `wait_windows_pids_gone` 那一处**，因为它直接决定切换要等多久。

**结论**：保留为待修项，**从 P0 下调为 P1**，且优先级排序应把 `wait_windows_pids_gone` 排在 `windows_workbuddy_process_rows_for` 之前。

## P0-2 首屏 1.40 MiB：真问题，但**影响被高估**

**「是不是有意为之」→ 否。** 依据：`App.tsx` 中 `lazy` / `Suspense` / 懒加载 / chunk 相关字样**零匹配**；全仓提交历史里与性能相关的只有 `e8c90a7 perf: Trae 分区切换不再整页重载（数据层 SWR 快照缓存）` —— 那次做的是**数据层**优化，打包层从未涉及。⇒ 未做过，不是刻意不做。

**但影响需要诚实下调**：
- 桌面端（Tauri）从**内嵌资源 / 本地磁盘**加载，WebUI 走 `127.0.0.1`。**都不跨网络** ⇒ 1.40 MiB 的代价主要是**解析**（数十 ms 量级），不是下载。
- recharts 在产物中的**确切占比未实测**（源码 5.1MB 不代表产物占比）。`components/ui/chart.tsx:2` 的 `import * as RechartsPrimitive` 确实会阻碍 tree-shaking，但能省下多少**必须量了才算**。

⇒ **修正后的定性**：真问题（未做），但**先量化再决定投入**。建议第一步只做一件事：拆一次 chunk 或跑一次可视化分析，拿到 recharts / radix / 其余 三者的真实字节数，再决定是否值得引入懒加载的复杂度（懒加载会牵动路由层 `Suspense` 与嵌入资源护栏，不是零成本）。

**不撤回的理由**：即便收益是数十 ms，「用户从未打开的 4 个统计页的图表库」在首屏就解析，是明确的浪费；且这是唯一一条能同时降低**内存占用**的优化。

## P0-3 网关池：**部分有意为之**

**「是不是有意为之」→ 是，且注释明确说了。** `trae/routes.rs:385`：

> 「每次选号前重新同步：另一个入口（签到页 / 桌面端）可能刚写了冷却或刷新了积分。」

⇒ 「重同步」这个**行为**是刻意的正确性设计，**不能改成 TTL 缓存**（我原报告已指出，这里再确认一次：这是硬约束，不是偏好）。

**但「每请求重建整个 `Vec` + 对每个账号做哈希派生」不是刻意选择**，而是实现方式。`pool.rs:237` 的注释还确认了关键前提：

> 「**设备标识不需要分家**：`device::derive(uid)` 是 uid 的纯函数、与变体无关」

⇒ 既然是纯函数、键空间 = 账号数（有界），按 uid 缓存它**不可能改变任何行为**。这一项是**无争议的安全优化**。文件读按 `(mtime, size)` 缓存同理：写必然改 mtime ⇒ 「一写即可见」的语义原样保留。

**结论**：真问题，但必须按「保住语义」的拆解法修，不能图省事加 TTL。

## P0-4 token 统计不缓存：**有意，但理由缺失 —— 需确认**

**「是不是有意为之」→ 存疑，必须问作者。** 依据：`token_stats.rs:1048` 把这件事写成了**设计属性**：

> 「`region=all` **实时聚合，不缓存、不落库**。」

用词是「不缓存、不落库」这种**断言式**表述（对比本仓库其它注释的「为什么…因为…」写法），但**没有给出理由**。它来自初始提交 `461827e`，无增量历史可追。

两种可能，处理方式完全不同：
- **若是刻意**：大概率是为了避免「落库的聚合值与真实日志不一致」这类陈旧状态问题（本仓库对「陈旧状态」极敏感）。那么**可以加内存缓存、但不能落盘**，且必须给出失效条件。
- **若只是描述现状**：那它就是未做的优化。

⇒ **修正后的定性**：**在向作者确认之前，不得按「缺陷」处理**。可先做的是**无争议的那半条**——`ide_workspace_meta` 被调在会话循环体内（`token_stats.rs:719`），把同一份 `index.json` 读 N 次，这是**纯冗余**，与「是否缓存聚合结果」无关，可以先改。

## P0-5 静态资源缓存头：确认为真问题（从未考虑过）

**「是不是有意为之」→ 否。** 全仓 `Cache-Control` / `ETag` / `Last-Modified` 只有两处匹配，都在 OAuth 结果页，且**有明确理由**：

```
crates/buddy-switch-core/src/modules/trae/oauth.rs:1486
/// `Cache-Control: no-store`：结果页含账号昵称（个人信息），且回调 URL 是**一次性**的
```

⇒ 说明团队**理解** HTTP 缓存语义并会按需使用，`static_handler` 没有缓存头是**没考虑过**，不是刻意留空。

**⚠️ 但加之前必须先确认一件事**（这条我原报告说了、这里再强调，因为它决定了「会不会破坏功能」）：桌面端更新后，**WebUI 页面上已经打开的浏览器标签**会怎样？若 `index.html` 被缓存，用户升级后会拿着旧的 `index.html` 去请求**已不存在的哈希 chunk** ⇒ 白屏。所以：`index.html` **必须 `no-cache`**，哈希资源才可 `immutable`。这不是可选项，是前置条件。

## P1-1 网关 5 次写锁：**底层设计有意，锁粒度是实现副产品**

`relay.rs:81`（增量 upsert、保留治理历史）、`:119`（在途租约）、`:145`（无论成败都释放，且注明「本次偏差见模块文档」）—— 这些注释表明**在途租约 + 熔断 + 增量同步**是有意设计，作者对边界情形有清醒认识。

⇒ 5 次 `pool.write().await` 是这套设计的**自然结构**，不是刻意选择。**结论**：是优化机会（合并同轮内的多次加锁、`acquire`/`release` 改原子量），但**任何改动都不得改变租约语义**。收益需在并发下才显现，**低优先级**。

## P1-2 core 的 async 阻塞：确认为真问题（**已在服务端路径证实**）

**「是不是有意为之」→ 否，是遗漏。** 决定性证据是**同一文件内的对照**：

```
crates/buddy-switch-server/src/api.rs:1582
    match trae::handlers::refresh_jwt_for(variant, user_id).await {   ← 未包 spawn_blocking
```

而**同一文件的 16 处邻居全部包了**（`:655` / `:880` / `:1286` / `:1298` / `:1355` / `:1376` / `:1441` / `:1467` / `:1512` / `:1604` / `:1618` / `:1632` / `:1646` / `:1662` / `:1675` …）。这是本项目「同款实现散落两处必须保持一致」纪律的典型违反。

## P1-3 Tauri 同步命令：真问题，但**必须分级**

**「是不是有意为之」→ 否。** 因为**约定是明文写死的**，`commands.rs` 自己写着：

```
:90-92  「Windows 的运行状态检测会启动 tasklist 子进程。同步 command 默认在 Tauri 主线程执行，
         标题栏拖拽期间一旦焦点事件触发状态刷新，就会阻塞原生窗口消息循环。
         放入 blocking 线程，保持窗口移动与 IPC 查询解耦。」
:150-151「async + spawn_blocking：状态检测可能执行 ps / helper 定位等子进程，
         避免在账号页挂载刷新时阻塞主线程造成页面卡顿。」
```

⇒ 判据很清楚：**「会起子进程」或「慢 IO」才必须 async + spawn_blocking**。

**所以 55 个同步命令不能一刀切**：
- **需要改**：做慢 IO 的那些 —— `get_trae_logs`（`:1306+`，全量读日志文件）、`list_sessions`（`:483`）、`import_local`（`:262`）、`get_trae_accounts`（`:1275`）、`get_trae_variants`（`:1260`，含进程探测）、`check_auth_permission`（`:338`，含 `std::fs::write`）。
- **不必改**：读一个小配置文件的那些（`get_switch_config`、`get_schedule_config`、`get_auto_checkin_config` 等）—— 它们是**微秒级**，改 async 反而多一次线程调度，属过度改造。

⇒ **修正后的定性**：真问题，但**按「是否慢 IO」分级**，不是「55 个都该改」。我原报告「55 个同步」的表述容易误导，这里更正。

## M3 `freshMs` 默认 0：**有意为之，不得按缺陷处理**

**「是不是有意为之」→ 是，且是文档化的核心语义。** `src/lib/use-cached-resource.ts:9-18` 的文档表写得很清楚：

> 「该键**已有**快照 → `loading=false` → **立刻渲染真数据，请求在后台跑**」

⇒ 这就是 **stale-while-revalidate**：挂载即后台重校验是**设计目标**（为了「切到 WorkBuddy 再切回 TraeWork 不闪骨架」），`freshMs=0` 是它的自然取值。

**修正后的定性**：我原报告把它列为「M3 缓存层默认每次挂载都重校验」是**误判**。它**不是缺陷**。唯一的讨论空间是：对**变化极慢**的数据（settings / schedule / variantStatuses）是否值得设 `freshMs` 以减少后台请求 —— 这属**调优取舍**（拿「少一次请求」换「最长 30s 陈旧」），**不是修 bug**。应由产品决定，不该由性能审计单方面改。

## 本轮复核的元结论

1. **「有优化空间」和「是缺陷」是两回事。** 本次 13 条里，有 **3 条是刻意设计**（P0-3 的重同步、P1-6a 的 2s 轮询、M3 的 `freshMs=0`），**1 条我判错**（P1-4 sticky）。
2. **最强的「是遗漏」证据，是同一仓库里已有对照实现。** P0-1（`platform.rs` 已优化）、P1-2（`api.rs` 16 处邻居已包）、P1-6b（两个兄弟 hook 已有门控）、P1-3（约定明文写死）—— 四条都靠这个判据定性，而不是靠我判断「这样写不好」。
3. **「函数存在但从无调用」≠「迟早出问题」。** P1-4 的教训：必须先查写入路径是否真的被调用。
4. **注释里写成断言、却没有「为什么」的地方，是风险点。** P0-4 的「不缓存、不落库」属此类 —— 不能替作者下结论。
5. **严重度必须结合调用频率。** P0-1 原本被我列为 P0，实际调用路径是冷的（且已有 3s 缓存 + spawn_blocking 两道缓解）⇒ 下调。
