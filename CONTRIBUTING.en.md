# Contributing

**Contributions of every kind are welcome — pull requests included.** Issues, documentation, bug fixes and features all count. This project is maintained by one person, and what it has to keep up with are several clients that change whenever they like — the reports and patches that come from the community are often exactly why it manages to keep up.

## What you can do

| Type | Notes |
| --- | --- |
| Report a problem | File a bug or a suggestion in [Issues](https://github.com/NextAgentX/trae-workbuddy-switch/issues). Include **steps to reproduce**, the **client version** and logs; strip tokens, account details and anything else sensitive before pasting |
| Fix a bug | A client update changed a data structure or an endpoint and something stopped working — these fixes are the most valuable kind |
| Support a new client version | Follow up on data-structure and endpoint changes in new client releases |
| Docs and translation | Correct outdated descriptions in the README / `docs/`, improve the Chinese or English wording |
| UI and UX | Frontend interaction, accessibility, dark-mode details (see [Frontend components](#frontend-components-shadcn-first)) |
| New features | Please open an Issue first to align on the direction, so you do not finish something only to find the approach disagrees |

## Before you open a PR

1. For larger changes, **open an Issue first** to discuss the direction; small fixes (typos, docs, clear-cut bugs) can go straight to a PR
2. Fork → create a branch (`fix/…`, `feat/…`) → commit → open the PR against `main`
3. Run at least this much locally:

```bash
npm install
npm run build     # tsc type check + API contract check (check:api) + frontend build
cargo test        # Rust unit tests
```

`npm run build` already includes `npm run check:api`; if you only touched the Rust side or the route table, running `npm run check:api` on its own is enough.

4. If you changed the UI, attach screenshots (ideally one light, one dark)

### PR checklist

- [ ] `npm run build` and `cargo test` both pass
- [ ] If you touched an API command name or a route ⇒ `npm run check:api` passes
- [ ] The diff contains no real credentials, local data files or logs
- [ ] Any new UI element is readable in dark mode
- [ ] For a bug fix, you explained the reproduction steps and the root cause, not just which line changed

## Repository conventions

### Commit messages

Use Conventional Commit prefixes (`feat:` / `fix:` / `docs:` / `refactor:` …) and **write the title and body in Chinese**, as this project does.

Release notes are generated by `scripts/gen-release-notes.mjs`, which groups commits by prefix and **takes only the first line of each commit** ⇒ that first line must stand on its own as a description of what changed.

### Frontend components: shadcn first

Decision order: reuse an existing component from `src/components/ui/` → compose existing shadcn components → if one is missing, add the shadcn/Radix implementation and wrap it in `src/components/ui/` → write a custom component only when the shadcn set and its composition APIs genuinely cannot meet the requirement, and document the reason in the code (**visual preference alone is not a reason**).

Custom components must still reuse the project's theme tokens (`primary` / `ring` / `border` / `popover` / `muted` / `destructive` / `brand`) and the existing density, radius and accessibility conventions. Use components for menus, overlays, dialogs, selects and tooltips — do not substitute native shortcuts such as `details` / `summary`.

The full rules live in [`.trellis/spec/guides/ui-component-guidelines.md`](.trellis/spec/guides/ui-component-guidelines.md).

### Adding an API command: everything that must stay in sync

The dual channel (the desktop app goes through Tauri invoke, the webui through local HTTP) means the same command name appears as a **plain string** in several places, with no compile-time protection. When you add or rename a command, all of these must change together:

| # | Location | Symptom if you miss it |
| --- | --- | --- |
| 1 | the `ROUTES` table in `src/lib/api.ts` | the webui throws "operation not supported" |
| 2 | the `call("<cmd>")` in `src/lib/api.ts` | nothing calls the command / it is reported as a dead route |
| 3 | the `.route(...)` in `crates/buddy-switch-server/src/api.rs` | webui returns 404 |
| 4 | `generate_handler![…]` in `src-tauri/src/lib.rs` | desktop reports command not found |
| 5 | `src/lib/screenshot-demo.ts` (**read-only** commands) | demo mode throws "missing read-only data" at runtime |

`npm run check:api` verifies every one of these alignments — just run it after your change.

> **A trap with "single `Value` parameter" commands**: if a command signature has **exactly one `Value` parameter** besides Tauri-injected ones, the frontend must pass it as the only top-level key (`call("x", { options: { … } })`) and must **not** flatten the arguments. Tauri looks values up **by parameter name**, so a flattened payload fails with `missing required key <name>`; the webui backend accepts both shapes ⇒ the symptom is "works in the browser, dead on the desktop". Check #7 of the contract script exists precisely for this.

### Display fields must be "string or null"

Display fields returned to the UI (account names, nicknames and the like) must be normalized to a string or `null`: `account::display_str` on the Rust side, `displayText` in `src/lib/display-text.ts` on the frontend. A dirty value (object, number, encrypted envelope) makes React unmount the whole tree ⇒ **blank screen**.

### Two intentional duplicate implementations

`src-tauri/src/commands.rs` and `crates/buddy-switch-server/src/api.rs` contain several **deliberately non-deduplicated** implementations (one per host). Change one and you must change the other, keep the "the two must stay in sync" comments that point at each other, and **add tests on both sides**.

### No dead code

When cleaning up, mind the "smallest committable unit": if A uses a **newly added symbol** in B, then B has to be committed in the same batch, otherwise that intermediate commit does not compile.

## Build and debugging tips

- The frontend bundle is embedded into the server binary at **compile time** (`rust-embed`) ⇒ after changing the frontend you must rebuild the host, or the UI will not change
- Stop any running `buddy-switch` before rebuilding, otherwise linking fails on Windows because the binary is locked
- On Windows, `LNK1104` or `拒绝访问 (os error 5)` is usually a transient conflict between concurrent compile jobs: retry, or use `cargo build -j 1`. It is **not a code error**
- Environment requirements, packaging and the release process: [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md)

## A few hard requirements

- **Never commit local data**: account stores, auth files, API keys, tokens and logs stay out of the repository. Re-read your diff before pushing and make sure no real credentials are in it
- **Never commit code of unknown origin**: anything borrowed from another project must be credited, and its license must be compatible
- **This project is licensed under the [PolyForm Noncommercial License 1.0.0](./LICENSE)**: by submitting a contribution you agree that it is distributed under the same license, and confirm you have the right to submit it. See [docs/LICENSING.md](docs/LICENSING.md)
- Do not paste complete tokens or account credentials in an Issue or PR, not even your own

## About the `reference/` directory

`reference/` holds **read-only reference material** extracted from the various clients and related projects, used to compare data structures and protocols. It is not part of this project's code — do not add business logic there, and do not treat it as an implementation source to copy from.

## Where to ask

- Usage questions, bugs, feature requests → [Issues](https://github.com/NextAgentX/trae-workbuddy-switch/issues)
- Security issues (credential leaks, unauthorized access, …) → please do **not** open a public Issue; contact the author privately first and describe the situation
